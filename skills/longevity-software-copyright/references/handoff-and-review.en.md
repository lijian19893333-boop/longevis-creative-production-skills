# Handoff and final review

## Package for the recipient

Ask who receives the result only if the conversation does not establish it. For an application drafter, use one short folder per software and a shared naming convention. Include only relevant completed files and explicit gap notes. A suitable pattern, adapted to the actual request:

```text
SoftwareName_Version/
  00_Read-first.txt
  01_Collection-form.docx + .pdf
  02_Main-functions.txt
  03_Operation-manual.docx + .pdf
  04_Design-description.docx + .pdf
  05_Program-materials.docx + .pdf       [only if actually prepared]
  06_Source-or-native-project.zip       [authorized and available]
  07_Supporting-evidence/               [authorized, as required]
  08_Gaps-and-confirmations.txt         [if needed]
```

The bracketed annotations explain the pattern; they are not filler files to create. If source is missing, supply a gap note instead of a document pretending to be code. APK and build records can remain in an internal evidence archive unless relevant to the drafter's request. Identity documents are private supporting material; include only for an authorized recipient, never in the public skill.

An internal working archive may contain source snapshots, file-order lists, page maps, comparison reports, render images, version history, installation evidence and hashes. Keep it separate from the concise handoff. Existing archives are preserved; update the current index and add a dated version, with source hashes if copying original evidence.

## Review the final package

| Check | Evidence |
|---|---|
| Template coverage | Every actual field addressed; unknowns/proposals visible |
| Main functions | Required character count plus source-based content review |
| Source scope | Included/excluded files, native export coverage, revision and ownership evidence |
| Program selection | All or traceable first/last ranges; no fillers; actual end boundary |
| Consistency | Same name/version, owner, dates, environment and capabilities throughout |
| Layout | Every PDF page viewed; tables, glyphs, images, code wrapping and page numbers readable |
| Source integrity | Selected text compared with originals; copy/ZIP checksums verified |
| Delivery | ZIP extracts and contains only intended files; final paths are usable |
| Remaining work | Specific per-software gaps, confirmation owner and effect on final filing |

Do not mark a case ready for final declaration while critical facts, source coverage or required supporting evidence remain unresolved. Continue all supported documents and give a concrete handoff rather than a generic checklist alone.

## Status wording

Use specific evidence: “editable materials prepared,” “source matches the listed snapshot,” “PDF pages visually inspected,” “sent to the drafter,” “submitted with receipt,” or “registered with certificate,” only when that event occurred. A local ZIP does not prove external receipt; a portal upload does not establish acceptance or registration. Summarize material limitations without hypothetical warnings.

## Sharing a reusable skill

Publish only an enumerated set of original reusable files. Inspect every candidate file and final archive for private data, local paths, secrets, filled examples and copied third-party template content. Keep synthetic tests clearly synthetic. Preserve the collection's license and naming conventions; verify remote bytes/commit and applicable CI before claiming publication. Public workflow release does not authorize publication of the user's application evidence.
