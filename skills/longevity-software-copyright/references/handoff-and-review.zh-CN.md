# 交接与终审

## 按接收人打包

会话已明确接收人时不重复问。交给软著撰写师，通常每款一个简明文件夹，命名规则一致，只放相关成品和明确缺口。按实际要求调整以下结构：

```text
软件名称_版本/
  00_先读说明.txt
  01_信息采集表.docx + .pdf
  02_主要功能.txt
  03_操作说明书.docx + .pdf
  04_软件设计说明书.docx + .pdf
  05_程序鉴别材料.docx + .pdf       [实际具备时]
  06_源码或原生工程.zip            [获准提供且已有时]
  07_证明材料/                    [获准提供，按要求]
  08_缺口与待确认.txt              [有缺口时]
```

方括号是结构解释，不是要创建填充文件。缺源码就提供缺口说明，不放冒充代码的文档。APK 和构建记录按撰写师需要提供，其余留内部证据归档。主体证件属于私有证明材料，只交获准接收人，不进入公开 Skill。

内部工作归档可保留源码快照、文件顺序表、行页映射、比对记录、渲染图、版本历史、安装证据和哈希，和简明交接包分开。保留历史版本，更新当前索引、增加带日期版本；复制原始证据时核对来源哈希。

## 终审表

| 核对项 | 核验依据 |
|---|---|
| 模板覆盖 | 实际字段逐项处理，未知和拟填项可见 |
| 主要功能 | 字数满足本次要求，且内容经源码／证据核对 |
| 程序范围 | 纳入／排除清单、原生导出范围、版本及权属依据 |
| 程序选取 | 全量或可追溯的首尾连续范围，不填充，核对结束位置 |
| 一致性 | 名称／版本、主体、日期、环境和功能前后一致 |
| 版式 | PDF 每页已查看，表格、汉字、图片、代码折行和页码可读 |
| 原文完整性 | 选取正文与原文比对，复制／压缩校验正确 |
| 交付包 | 能解压，只有预期文件，最终路径可用 |
| 剩余工作 | 逐款列明缺什么、谁确认、对最终申报有何影响 |

关键事实、程序覆盖或必要证明未解决时，不标成可以完成最终声明。继续完成有依据的文档，交付具体材料，不能只给通用清单。

## 状态表述

按实际事件表述：“可编辑材料已整理”“源码与列入的快照一致”“PDF 已逐页目检”“已发撰写师”“已递交并有回执”“已登记并取得证书”。本地压缩包不证明外部已接收，页面上传不证明已受理或登记。说明实际限制，不扩展假设性警告。

## 将流程公开为 Skill

只公开枚举后的自有通用文件。逐一检查候选文件与最终压缩包，排查隐私、本地路径、密钥、已填案例和第三方模板内容。合成测试明确使用合成数据。沿用技能库许可与命名约定，核对远端内容／提交和适用的自动检查后再报告发布。公开工作方法不授权公开用户的申请证据。
